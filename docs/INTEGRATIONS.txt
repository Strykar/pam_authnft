pam_authnft integration contracts
=================================

Purpose
-------

pam_authnft is small on purpose. It does one job — pin an authenticated
session to a kernel-enforced network identity — and delegates everything
else to external tools. This document specifies the public contracts
external projects use to integrate with pam_authnft, so third parties
can implement producers, consumers, and tooling without reading the
module source.

The module is not a plugin host. There is no shared-library ABI, no
dynamic loader, no callback registry. Every contract described here
uses an existing kernel or userspace primitive (PAM environment, kernel
keyring, filesystem, D-Bus, netlink) with a narrow, documented schema.
This is deliberate: fewer moving parts, broader composability, and no
linkage between projects means no shared trust boundary.


Status labels
-------------

Each contract carries a status label:

    stable   Load-bearing in the current release. Breakage is a bug.
    draft    Implemented but subject to refinement. Producers should
             pin to the current release and watch the changelog.
    future   Identified need without a shipped mechanism. A producer
             wanting this integration should open an issue so the
             contract can be designed before code lands.


1. PAM stack composition
------------------------

Status: stable

pam_authnft is a PAM session module. Its behaviour is governed by the
standard Linux-PAM contract (pam.conf(5)) plus the items below.

1.1 Stack ordering

    session required pam_unix.so           # or similar, sets PAM_USER
    session optional pam_systemd.so        # optional, unrelated
    session optional <producer>.so         # any claims_env producer
    session required pam_authnft.so claims_env=MY_KEY

Any module that wants to influence pam_authnft's behaviour via a PAM
environment variable MUST run before pam_authnft in the session stack.
Ordering within the PAM stack is the admin's responsibility; the module
does not attempt to re-invoke producers.

1.2 PAM items read

pam_authnft reads the following items from the PAM handle:

    PAM_USER   — authenticated username. Required. Validated against
                 a conservative character set before any interpolation.
    PAM_RHOST  — optional. Source IP literal or hostname depending on
                 sshd UseDNS setting. See pam_authnft(8) for the three
                 supported rhost_policy modes.

No other PAM items are consulted.

1.3 PAM environment variables read

pam_authnft reads at most one PAM environment variable, whose name is
supplied by the operator via the claims_env=NAME module argument (see
§2 below). Module arguments are not inherited from environment.

1.4 PAM data keys

pam_authnft owns pam_set_data key "authnft_cg_id". Other modules MUST
NOT read, write, or free this key. The stored value shape is an
internal ABI and may change between releases.

The key name is retained for historical reasons even though the stored
value now includes more than just the cgroup ID (see invariant #3 in
CONTRIBUTING.txt).


2. claims_env contract (keyring payload channel)
------------------------------------------------

Status: stable

A producer that wants to surface small session metadata — audit IDs,
claim tags, session handles — in the nftables element comment emitted
by pam_authnft SHOULD use this contract. The payload is opaque to
pam_authnft; sanitization and truncation are performed on read.

2.1 Transport

    Producer                                 Kernel                 pam_authnft
    --------                                 ------                 -----------
    add_key("user", desc, payload,   -->     keyring
            len, anchor)                     allocates
                                             serial = N
    keyctl(KEYCTL_SET_TIMEOUT, N, ttl)
    keyctl(KEYCTL_SETPERM, N, perms)
    pam_putenv(pamh, "NAME=N")       -->     PAM env
                                             "NAME=N"     -->       pam_getenv("NAME")
                                                                    keyctl(KEYCTL_READ, N, ...)
                                                                    sanitize + truncate
                                                                    embed in nft comment

2.2 Producer requirements

    MUST use pam_putenv(3) to set the env variable. pam_authnft reads
    it with pam_getenv(3), which sees only the PAM environment. libc
    putenv(3) writes the process environment instead: sshd's
    import_environments() replays pam_getenvlist(3) entries into the
    PAM handle that runs the session stack, but process-environment
    strings are exported to the user session only, so a putenv(3)
    value silently fails to reach pam_authnft.

    MUST use the "user" key type. Other types (keyring, logon, big_key)
    are not supported.

    MUST place a non-empty payload in the key. Zero-byte payloads are
    treated as "no tag available" by the consumer.

    MUST NOT include NUL bytes in the payload. The consumer sanitizer
    stops at the first NUL by design and producers that embed one will
    see their payload truncated.

    SHOULD anchor the key in KEY_SPEC_SESSION_KEYRING (-3). If the PAM
    stack does not run pam_keyinit before the producer, this anchor
    will fall back to the user keyring; behaviour in that configuration
    is undefined but currently works on stock Arch, Debian, and RHEL.

    SHOULD call KEYCTL_SET_TIMEOUT before KEYCTL_SETPERM. Setting perms
    first drops SETATTR, which blocks subsequent timeout updates.

    SHOULD set KEYCTL_SETPERM to KEY_POS_VIEW|KEY_POS_READ|KEY_POS_SEARCH
    only (POSSESSOR bits). Do not grant write to GROUP or OTHER.

    SHOULD cap payload length at 256 bytes. The consumer truncates at
    CLAIMS_TAG_MAX (192 bytes after sanitization) and the extra headroom
    covers the ratio of unsafe-byte expansion, if any.

    SHOULD use a description prefix unique to the producer project
    (e.g., "foo_<session_id>") to avoid collisions if multiple producers
    run in the same stack.

2.3 Consumer behaviour

    Reads the payload with keyctl(KEYCTL_READ).

    Sanitizes to the character class [A-Za-z0-9_=,.:;/-]. Every byte
    outside the class is replaced with '_'.

    Truncates at CLAIMS_TAG_MAX bytes.

    Embeds the sanitized tag in the nftables element comment as
    "<user> (PID:<pid>) [<tag>]".

    Non-fatal on every failure: missing env var, non-numeric value,
    unknown serial, permission denied, empty sanitized output. In any
    of these cases pam_authnft emits the element with the legacy
    comment ("<user> (PID:<pid>)") and continues.

2.4 Payload format

pam_authnft imposes no structure. Producers MAY ship:

    audit-session:7f3e9a
    0123456789abcdef
    role=db-reader
    ticket-4218/approved-by-ops
    runbook=RB-0091,shift=night

— anything readable to an operator running `nft list set inet
authnft session_*_cg`. The contract is "printable ASCII, bounded
length, producer-defined meaning." pam_authnft does not parse,
interpret, or validate the payload structure; it is an opaque tag
displayed verbatim (after sanitization) in the element comment.

2.5 Security note

The producer is inside the trust boundary. The payload is not
authenticated — any module in the PAM stack that can write the key
can supply any tag. The sanitization protects the nftables command
stream from injection; it does NOT protect against a hostile producer.
Operators SHOULD ensure all producers in their PAM stack are
root-trusted.


3. Non-PAM producer contracts
-----------------------------

Status: future

Tools that operate outside the PAM stack — for example, sshd
AuthorizedKeysCommand helpers — cannot call pam_putenv and therefore
cannot use §2 directly. Three candidate bridges have been identified;
none have shipped.

3.1 SSH environment injection (proposed)

sshd accepts `environment="NAME=value"` prefixes in authorized_keys
entries. An AuthorizedKeysCommand can emit these; they become part of
the session's environment and are visible to pam_authnft via getenv(3).

A small consumer-side change (new module arg, say env_source=session)
would switch the claims lookup from pam_getenv() to getenv(). The
producer-side requirement reduces to "emit an environment= directive
carrying the key serial."

Before this becomes stable, pam_authnft needs a design for how
environment= interacts with the keyring ACL. A serial written by an
unprivileged helper is not readable by root without relaxing perms to
KEY_POS_READ on OTHER, which widens the threat model.

3.2 User keyring via @u (proposed)

A non-PAM producer running as the target UID can anchor its key in
KEY_SPEC_USER_KEYRING (-4) instead of the session keyring. The user
keyring is persistent across sessions and readable by root (via
KEYCTL_SEARCH starting from the user keyring).

pam_authnft would need an additional lookup path or an explicit module
arg (e.g., keyring_anchor=user) to fall through to @u when the PAM
env var is absent. Producer still needs a way to communicate the
serial — likely a file drop in /run/<producer>/, which defeats the
benefit of using the keyring at all.

3.3 Tmpfs-resident state file (pragmatic fallback)

A producer publishes `/run/<producer>/<session_id>` atomically via
write-to-temp + rename(2) into a tmpfs directory owned by root. The
file contains a single `KEY=value` line (or a small structured
format). pam_authnft reads the file, validates ownership and mode,
and injects the value.

This mirrors the standard Linux convention used by /run/systemd,
/run/udev, and /run/user for ephemeral state exchanged between
root-trusted components. It is the simplest bridge and the one most
likely to ship first. The downside is re-implementing the cleanup and
lifetime semantics that the kernel keyring handles for free.

Projects interested in a non-PAM producer bridge should open an issue
describing the use case before implementing against any of these
sketches — the shipped design may look different.


4. Nftables fragment contract
-----------------------------

Status: stable

pam_authnft loads a per-user nftables fragment on every open_session
where the user is a member of the `authnft` group. The fragment is the
primary integration point for configuration-management tools, identity
brokers, and policy engines.

4.1 File location and ownership

    Path:      /etc/authnft/users/<username>
    Owner:     UID 0 (root), GID any
    Mode:      any mode with no S_IWOTH bit set (stat().st_mode & S_IWOTH == 0)
    Encoding:  UTF-8 per nftables' lexer; 7-bit ASCII is safe

4.2 Sets available to the fragment

pam_authnft creates three per-session sets in `table inet authnft`
before loading the fragment. Fragments reference them via four
placeholders that are substituted at session-open time:

    @session_v4     per-session set: socket cgroupv2 level 2 . ip saddr
    @session_v6     per-session set: socket cgroupv2 level 2 . ip6 saddr
    @session_cg     per-session set: socket cgroupv2 level 2 (cgroup only)
    @session_chain  per-session chain name (@ stripped, bare identifier)

A session element goes into exactly one set: IPv4 addresses (including
v4-mapped v6 addresses extracted to plain IPv4 during normalization)
land in the v4 set; pure IPv6 addresses in v6; absent or unparseable
PAM_RHOST values in the cg-only set.

Substitution is applied to the top-level fragment only. Files pulled
in via nftables `include` are parsed by libnftables directly and do
not receive substitution. Each session's nft_ctx is independent;
concurrent sessions never share variable state.

Fragments reference per-session sets and chain via placeholders:

    add rule inet authnft @session_chain \
        socket cgroupv2 level 2 . ip saddr @session_v4 \
        tcp dport { 22, 443 } accept

    add rule inet authnft @session_chain \
        socket cgroupv2 level 2 @session_cg \
        tcp dport 8080 accept

Fragments SHOULD NOT redeclare per-session sets. A redeclaration with
an incompatible type would fail the transaction and deny the session.

4.3 Chains available to the fragment

pam_authnft creates a shared base chain and a per-session chain:

    chain filter {
        type filter hook input priority filter - 1;
        policy accept;
        ct state established,related accept
        jump session_<user>_<pid>     # one per active session
    }

    chain session_<user>_<pid> {
        # fragment rules land here via @session_chain placeholder
    }

Fragments add rules into their per-session chain via
`add rule inet authnft @session_chain ...`.

A top-level fragment MUST NOT add rules to the shared `filter` chain.
`add rule inet authnft filter ...` is rejected and the session is
denied, because such a rule persists across sessions and affects every
other session's traffic. Shared-chain rules belong in an included file,
which is the composition mechanism §4.6 describes and the only place
the validator permits them.

Wherever they land, shared-chain rules SHOULD NOT use drop or reject
actions: they persist across sessions and affect all traffic.

Fragments MAY create additional chains; these are not cleaned up by
pam_authnft and persist for the table's lifetime.

What the validator checks, and where it stops:

    top-level fragment    verb denylist, shared-chain guard,
                          include-path rules
    included file         verb denylist, include-path rules
                          (shared-chain guard deliberately relaxed,
                          see §4.6)

Both are scanned. Before the fix for issue #108 the scan covered only
the top-level buffer while libnftables resolved includes at execution,
so an included `flush ruleset` ran and the module reported success.
Included files are now opened, permission-checked to the same bar as
the top-level fragment (root-owned, not group- or world-writable,
regular file, in a 0700 root:root directory)
and scanned, to a depth of 4 and a total of 16 files, with repeats and
cycles rejected.

4.4 Programmatic fragment generation

Tools that generate fragments (Ansible roles, Salt states, bespoke
identity brokers) SHOULD:

    Write to /etc/authnft/users/<username> with mode 0644 and uid 0.
    Use a temporary file + rename(2) for atomicity.
    Validate the fragment with `nft -c -f <file>` before installing.
    Track generation provenance in a comment block for operator sanity.

Permissions the module enforces at every open_session, on the fragment
and on every file it includes:

    the file           root-owned, and not writable by group or other.
                       0644 and 0600 both pass; 0664 does not.
    its directory      root-only, 0700 root:root. Nothing may be
                       readable, writable or traversable by group or
                       other.

The directory is the check that carries the confidentiality. With 0700
a non-root user cannot traverse in, which is what makes a 0644 fragment
safe. Without it, 0644 exposes every user's network policy to every
local user.

Group-write on the file is rejected because the `authnft` group is
exactly the set of users the module gates. A 0664 root:authnft fragment
would let any gated user rewrite the rules another one receives at their
next login, installed as root.

A producer using a config-management tool must set the mode explicitly.
Ansible's copy and template default to 0644, which passes, but they do
not create the parent directory 0700. Failure is fail-closed: the
session is denied and the reason is logged.

The module does not signal producers on fragment reload; fragments are
re-read on every open_session.

4.5 Element timeout

pam_authnft inserts session elements with a 1-day timeout as a safety
net. Primary cleanup is close_session (which tears down the per-session
chain, sets, and jump rule). Fragments MUST NOT insert their own
elements into per-session sets; these are owned by pam_authnft.

The nft transaction is three separate nft_run_cmd_from_buffer calls.
If call (c) fails (e.g., a syntax error in the fragment), the
per-session chain, sets, and jump rule from calls (a) and (b) remain.
The session is denied with PAM_AUTH_ERR. The orphaned per-session
state has no matching fragment rules and is reaped at the next session
close or manually via `nft delete table inet authnft`.

4.6 Composing fragments via nftables `include`

libnftables resolves `include` directives transitively when processing
a user fragment. A per-user fragment MAY pull in shared rules from a
common file, letting a site maintain base policy once and override or
extend it per user.

The shared `filter` chain is an included file's documented destination,
which is why the shared-chain guard of §4.3 does not apply here. Every
other check does: the verb denylist is enforced on included content,
and each included file must be a root-owned, non-world-writable regular
file under /etc/authnft/. Nesting is capped at 4 levels and 16 files
total; a file that includes itself, or that is included twice, is
rejected. A rejection denies the session.

Convention: keep shared fragments under a subdirectory of
/etc/authnft/ (for example, /etc/authnft/groups/) and reference them by
absolute path from the user fragment:

    # /etc/authnft/groups/sre-oncall.nft
    # Included files do NOT receive placeholder substitution.
    # Use the shared filter chain with accept-only rules.
    add rule inet authnft filter \
        ct state new tcp dport { 22, 443, 9090 } accept

    # /etc/authnft/users/alice
    # Top-level fragment uses placeholders for per-session policy.
    include "/etc/authnft/groups/sre-oncall.nft"
    add rule inet authnft @session_chain \
        socket cgroupv2 level 2 . ip saddr @session_v4 \
        tcp dport 5432 accept

The included file's rules land in `chain inet authnft filter`
(shared); the user fragment's rules land in the per-session chain
(via @session_chain substitution). Two patterns for composition:

    Per-session policy in the top-level, shared policy in includes.
    The per-user fragment uses placeholders for its own rules. The
    included fragment uses the shared filter chain — no placeholders.

    Fully-generated per-user fragments (for automation). A producer
    generates the full fragment text, inlining any shared rules.
    Placeholders are substituted at session-open time as normal.

Hand-written fragments that use @session_v4 inside an included file
will fail to load: libnftables parses the literal token @session_v4
as a set reference, the set does not exist, and the session is
denied. This is a detectable failure, not a silent one.

Security considerations:

    pam_authnft enforces ownership (UID 0) and non-world-writable
    mode on the per-user fragment at /etc/authnft/users/<username>
    (see §4.1). It does NOT recurse into `include`d files. The admin
    is responsible for ensuring every transitively included file is
    also root-owned and not group- or world-writable, in a 0700
    root:root directory. A root-owned user
    fragment that includes an attacker-controlled file gives the
    attacker control over the loaded ruleset.

    As a safe default, include only from paths under /etc/authnft/.
    Do not accept include paths that are writable by any non-root
    account.

    libnftables does not detect include cycles. A fragment that
    includes itself (directly or through a chain of other fragments)
    will exhaust stack and abort the session transaction. Cycle
    avoidance is the admin's responsibility — a linter such as
    `nft -c -f /etc/authnft/users/<username>` will catch cycles at
    install time.

Operational notes:

    Rules added via `include` are indistinguishable from inline rules
    in `nft list` output. If provenance matters for audit, add a
    one-line `comment "..."` on each rule identifying the source
    fragment.

    Shared fragments are re-read on every open_session; a change to
    a group fragment takes effect on the next session open for every
    user whose fragment includes it. There is no signal mechanism to
    reload currently-active sessions.


5. Systemd scope and slice contracts
------------------------------------

Status: stable

Every session opened through pam_authnft is placed in a transient
systemd scope. External tools that want to observe or constrain
sessions integrate with systemd's scope/slice model.

5.1 Unit naming

    Slice:  authnft.slice
    Scope:  authnft-<username>-<session_pid>.scope

The slice is shipped in the package (data/authnft.slice). Operators
apply combined limits via systemd.resource-control(5) directives on
the slice.

5.2 External discoverability

A running session can be located via:

    systemctl --type=scope --no-pager list-units 'authnft-*.scope'
    systemd-cgls /authnft.slice
    cat /sys/fs/cgroup/authnft.slice/authnft-<user>-<pid>.scope/cgroup.procs

Tools that correlate nftables elements to scopes can read the element
comment (see §6.1) to recover <username> and <pid>.

5.3 Per-user resource limits

Operators MAY create drop-in directories for per-user limits:

    /etc/systemd/system/authnft.slice.d/<user>.conf

pam_authnft does not generate these. They are outside the module's
scope; the systemd documentation is authoritative.

5.6 Session-identity files

Status: stable (schema v=2)

pam_authnft writes a per-session JSON file at
/run/authnft/sessions/<scope_unit>.json on **successful** open_session,
and removes it on close_session. A failed open_session writes no file
(the scope and per-session nft state are also rolled back; see
docs/ARCHITECTURE.txt "Failed-open rollback"). Consumers may rely on
the existence of <scope_unit>.json as proof that the corresponding
session reached `nft_handler_setup` success.

The file exposes the same identity data that pam_set_data holds
internally (§1.4), without requiring a PAM handle or privileged
access to module source. This is the read-side observability
contract for SIEM agents, workload schedulers, container runtimes,
and operator dashboards.

5.6.1 Location and lifecycle

    Directory:  /run/authnft/sessions/    (0755 root:root)
    File:       /run/authnft/sessions/<scope_unit>.json
    Perms:      0640 root:root (root-only; see §5.6.5)
    Atomicity:  tempfile + rename(2) — readers never see a partial
                write. Intermediate name is .<scope_unit>.tmp.
    Lifecycle:  written after nft_handler_setup succeeds at open;
                unlinked by close_session. Orphans from crashed or
                skipped close paths are reaped by systemd-tmpfiles
                (MaxAge=7d) per data/authnft.tmpfiles.

5.6.2 Schema

    {
      "v": 2,
      "cg_path": "authnft.slice/authnft-alice-4321.scope",
      "user": "alice",
      "remote_ip": "2001:db8::1",
      "fragment": "/etc/authnft/users/alice",
      "claims_tag": "role=db-reader",
      "scope_unit": "authnft-alice-4321.scope",
      "opened_at": "2026-04-16T09:12:17Z"
    }

Field semantics:

    v           integer, schema version. Currently 2. v=1 used a
                numeric cg_id (cgroupv2 inode); v=2 replaced it with
                cg_path (string). Additive changes MAY add fields
                without bumping v; removals or renames bump under
                the §8 rules.
    cg_path     string, cgroupv2 scope path without leading slash
                (e.g., "authnft.slice/authnft-alice-4321.scope").
    user        string, PAM_USER. Charset [A-Za-z0-9._-], max 32.
    remote_ip   string, normalized source IP in canonical form; v4-mapped
                v6 addresses are extracted to plain IPv4 literals. "" on
                the cg-only path (rhost_policy=lax with unparseable
                PAM_RHOST) or when rhost_policy=kernel failed and fell
                back.
    fragment    string, absolute path to the per-user nftables
                fragment that was candidate for loading. Readers
                cross-referencing `nft list table inet authnft` can
                infer whether the fragment was actually applied.
    claims_tag  string, sanitized keyring payload. "" when claims_env
                is not configured, the env var is absent, or the
                payload sanitizes to empty (§2).
    scope_unit  string, systemd scope unit name (§5.1).
    opened_at   string, RFC 3339 / ISO 8601 UTC timestamp.

All string fields are ASCII-safe by construction — producer-validated
upstream, no JSON escaping applied. Readers MAY assume no embedded
quote or backslash characters in string values.

5.6.3 Reader guarantees

    Readers MAY open the file at any time between the write and the
    unlink. The file is never absent-but-should-be during that window
    because the write is atomic.

    Readers MUST tolerate an ENOENT on open — the session may have
    just closed, or may have failed to create the file (the session
    itself proceeds regardless of a write failure).

    Readers MUST tolerate additive schema changes — a future field
    beyond those listed above is not a schema break. Reject only if
    `v > your_supported_version` and you require strict version
    matching.

5.6.4 Writer failure modes

pam_authnft logs at LOG_WARNING and continues if any step of the
write path fails (open, write, rename). The session establishment is
NOT failed — the file is best-effort observability, not a prerequisite
for session correctness. Common causes of write failure:

    /run/authnft/sessions/ missing — tmpfiles.d not installed, or
        systemd-tmpfiles not yet run after install. Operators SHOULD
        run `systemd-tmpfiles --create /usr/lib/tmpfiles.d/authnft.conf`
        after install.

    /run full — rare on modern hosts; operators monitoring tmpfs
        capacity will already alert on this.

    Filesystem mounted read-only — typically a deliberate hardening
        choice; affected operators should disable the file-writing
        step by applying a seccomp profile or LSM rule externally.

5.6.5 Security note

The file is root-only (0640 root:root). Most fields (cg_path, user,
remote_ip, scope_unit) are not secret — cgroup membership is
enumerable from /proc and PAM_USER is in `last`, `utmp`, and syslog.
The exception is claims_tag, which may carry token-derived material
(JTI, scope, session correlator) that is NOT derivable from /proc,
`last`, or `utmp`. An earlier version made the file group-readable
(0640 root:authnft) so unprivileged monitoring agents could read it,
but membership in the authnft group is exactly what gates a session,
so the group is the monitored-subject population — group-readable let
any managed user read every other managed user's claims_tag. That
contradicted the keyring UID-lock the module advertises (§2, ADMIN_GUIDE.md),
so the file is now root-only.

Non-root observation: a site that needs an unprivileged agent to read
these files should create a dedicated observer group distinct from
authnft and grant it via a drop-in that fchowns the files (the
group-read bit is retained so no code change is needed). Do NOT reuse
the authnft group for this. The claims_tag itself is also available
root-only in the nftables element comment (`nft list table inet
authnft`) and in the journal (AUTHNFT_CLAIMS_TAG), both privileged
surfaces, so a root SIEM loses nothing from the file being root-only.

Operators concerned about information exposure (e.g., claims_tag
containing audit correlation tokens) MAY mount `/run/authnft` with
stricter permissions via a drop-in mount unit; the file write will
still succeed as root.


6. Observability and audit contracts
------------------------------------

Status: stable

6.1 Nftables element comment format

Every session element carries a comment string:

    "<username> (PID:<session_pid>)"              # without claims_env
    "<username> (PID:<session_pid>) [<tag>]"      # with claims_env

<tag> is the sanitized payload from §2. Operators SHOULD parse with
this grammar, not by regex on the raw nft output:

    comment         = username " (PID:" pid ")" [ " [" tag "]" ]
    username        = 1*32( ALPHA / DIGIT / "_" / "-" / "." )
    pid             = 1*10DIGIT
    tag             = *192( ALPHA / DIGIT / "_" / "=" / "," / "." /
                            ":" / ";" / "/" / "-" )

Future extensions to the comment format will be announced in the
changelog and released under a new stable tag.

6.2 Structured audit events (journald)

Status: stable (field schema v=1)

Every open_session success emits a structured journal entry with
AUTHNFT_EVENT=open; every close_session that observed a prior open
via pam_set_data emits AUTHNFT_EVENT=close. Both share a
per-session AUTHNFT_CORRELATION token so a SIEM can join the two
events (and, by convention, the upstream authentication event that
produced the same token). This is the machine-readable audit-trail
surface for compliance reviewers and SIEM pipelines.

6.2.1 Identifier

    SYSLOG_IDENTIFIER=pam_authnft

Filter with `journalctl -t pam_authnft` or match on
`SYSLOG_IDENTIFIER=pam_authnft` in journald exporters.

6.2.2 Fields

Common to both events:

    AUTHNFT_EVENT         "open" | "close"
    AUTHNFT_USER          PAM_USER (charset [A-Za-z0-9._-], max 32)
    AUTHNFT_CG_PATH       cgroupv2 scope path string
    AUTHNFT_CORRELATION   shared token joining this event to its
                          pair. Class: [A-Za-z0-9_.:-]

Open-only:

    AUTHNFT_REMOTE_IP     normalized source IP, or "" on cg-only path
    AUTHNFT_FRAGMENT      absolute path to the candidate fragment
                          (/etc/authnft/users/<user>)
    AUTHNFT_CLAIMS_TAG    sanitized keyring payload (§2), "" if none
    AUTHNFT_SCOPE_UNIT    systemd scope unit name (§5.1)

Human-readable MESSAGE is also set (see journalctl default output):

    session opened: user=<u> cg=<path> remote=<ip> corr=<token>
    session closed: user=<u> cg=<path> corr=<token>

PRIORITY is LOG_INFO (6). No event is currently emitted at a higher
priority — operator-facing errors still land via pam_syslog(3).

6.2.3 Correlation token sources

pam_authnft resolves AUTHNFT_CORRELATION at open_session from, in
order:

    1. PAM env "AUTHNFT_CORRELATION", set by an upstream module via
       pam_putenv(3). Sanitized to the class above; characters
       outside the class are dropped. Empty-after-sanitize falls
       through to the next step.

    2. Synthesized token of the form
       "authnft-<unix_seconds>-<pid>-<8 hex random>". Uses
       clock_gettime(2) + getrandom(2) + getpid(2); no new syscalls.

The same token is stored in authnft_session_t (invariant #3) and
reused at close_session, so a close-side producer has no work to do.

6.2.4 Producer contract for upstream correlation

A PAM auth module (e.g., an identity broker that stamps session
audit logs with its own trace ID) SHOULD set AUTHNFT_CORRELATION
via pam_putenv(3) before pam_authnft runs:

    pam_putenv(pamh, "AUTHNFT_CORRELATION=<producer-trace-id>");

Character class: [A-Za-z0-9_.:-]. Length: unbounded at input;
pam_authnft truncates at CORRELATION_ID_MAX = 64 bytes after
sanitization. Other bytes are silently dropped (not substituted)
to keep tokens short.

If the upstream log stream already carries the same trace ID, a
reviewer can join authentication and session events across streams
without any shared database — just grep on the correlation value.

6.2.5 Delivery guarantees

sd_journal_send(3) writes to /run/systemd/journal/socket. On success
the entry is durably queued for journald before the syscall returns.

If the socket is unreachable (non-systemd host, sandbox restriction,
filesystem issue), pam_authnft falls back to pam_syslog(LOG_INFO)
with the same correlation token and a note that the journal was
unavailable. SIEM consumers that ingest both journald and syslog
will capture the event either way.

The session is NEVER failed on an audit-emit error — audit
observability is secondary to the PAM lifecycle.

6.2.6 Free-form pam_syslog(3) lines

In addition to the structured events above, pam_authnft emits
operator-facing log lines via pam_syslog(3) with the facility and
identifier chosen by the calling PAM application (typically sshd →
LOG_AUTH, ident "sshd"). These have free-form prose prefixed with
"authnft:" and cover error paths not otherwise visible:

    authnft: cleanup failed for <user>
    authnft: PAM_RHOST/kernel peer divergence: ...
    authnft: missing fragment for <user> at ...
    authnft: insecure permissions on ...

Consumers that need a complete audit trail SHOULD subscribe to
both the structured AUTHNFT_EVENT= entries (for happy-path session
lifecycle) and the "authnft:" prose (for error conditions).

6.2.7 Linux audit subsystem (AUDIT_USER_ERR)

Status: stable (operation tag, reason vocabulary)

Every fragment-rejection path in pam_authnft also emits a parallel
record via the Linux audit subsystem (audit(7)), routed through
libaudit's audit_log_user_message() at type AUDIT_USER_ERR (1109).
The pam_syslog(3) channel above stays in place; the audit channel
is additive, intended for SOC pipelines that scrape
/var/log/audit/audit.log instead of /var/log/auth.log.

The kernel-emitted record looks like (one line, wrapped here):

    type=USER_ERR msg=audit(1759334400.123:42): pid=1234 uid=0
        auid=1000 ses=3 subj=... msg='op=authnft-fragment-reject
        reason=missing user="alice"
        fragment="/etc/authnft/users/alice"
        exe="/usr/sbin/sshd" hostname=? addr=? terminal=?
        res=failed'

The application-supplied fields inside msg='...':

    op=authnft-fragment-reject  fixed; SIEM rules can string-match
    reason=<short-id>           one of:
        missing      stat() on the fragment failed
        perms        not root-owned, or world-writable
        content      verb scan / include path validator rejected
        nft-syntax   libnftables rejected at load time
    user="<pam_user>"           passes util_is_valid_username,
                                so [A-Za-z0-9._-] only — no audit
                                escaping concerns.
    fragment="<rules-dir-path>" /etc/authnft/users/<user>

`auid` (audit-uid) is set by an upstream PAM module (typically
pam_loginuid before pam_authnft); pam_authnft itself does not set it.
The user= field in msg='...' is the application's view of the
session user, which may differ if a misconfigured PAM stack runs
pam_authnft outside the user's session.

Producer/consumer notes:
  - Failure to open the audit netlink (subsystem disabled, missing
    CAP_AUDIT_WRITE) is non-fatal: the rejection still propagates as
    PAM_AUTH_ERR. Consumers SHOULD NOT rely on audit emission for
    correctness — only for observability.
  - The seccomp allowlist already covers the syscalls libaudit uses
    (socket, sendto, sendmsg, close); no additional sandbox surface.

6.3 Cgroup correlation

The cgroup path embedded in the per-session sets
elements is the cgroupv2 scope path from §5. The kernel resolves
this path to an inode at rule-load time. Correlation:

    cg_path from nft element (e.g., "authnft.slice/authnft-alice-4321.scope")
    → /sys/fs/cgroup/authnft.slice/authnft-alice-4321.scope

This is the recommended path for observability tools that want to
trace a packet (via `nft monitor trace`) back to a session.


7. Producer categories
----------------------

Status: informational

pam_authnft is agnostic about where payloads and fragments originate.
Any tool that satisfies the relevant contract in §1 through §6 is a
valid producer. The categories below are descriptive, not prescriptive:
a project may fit one, several, or none of them.

    PAM modules that run in-stack
        Participate in §1 (stack ordering, PAM items, env vars) and
        may use §2 (keyring payload) natively via pam_putenv. This is
        the shortest integration path.

    Programs invoked by sshd outside the PAM stack
        AuthorizedKeysCommand, ForceCommand wrappers, and similar
        hooks run before or alongside PAM and cannot call pam_putenv.
        They need one of the bridges in §3, all currently future.

    Out-of-band fragment generators
        Configuration-management tools (Ansible, Salt), policy brokers,
        inventory-driven automation. Integrate via §4 by writing files
        to /etc/authnft/users/. Do not participate in §2 unless they
        also run code in-stack.

    Observability and audit consumers
        SIEM collectors, tracing tools, resource-accounting daemons.
        Read the contracts in §5 and §6. Do not write anything
        pam_authnft depends on.

Projects that implement a producer or consumer role may self-nominate
for listing in a future ECOSYSTEM.txt file. A listing implies neither
endorsement nor interoperability testing.


8. Versioning
-------------

The contracts in this document are versioned independently from the
pam_authnft package version. Backwards-incompatible changes require a
new major version of the module and a minimum one-release deprecation
window with the old contract continuing to work.

Contract version: 1.0 (first release covering §1, §2, §4, §5, §6).

8.1 Tag content is opaque

The keyring payload described in §2 is a byte string. pam_authnft does
no semantic parsing: it reads the payload, applies the sanitization
rule in §2.3, truncates to CLAIMS_TAG_MAX, and embeds the result in
the comment grammar of §6.1. The payload carries no in-band version
field and the consumer performs no runtime version negotiation;
contract identity is established at module-version granularity, not
per-session.

8.2 Forward compatibility — additive-only at the wire

Future contract revisions MUST be additive at every boundary the
consumer observes: keyring transport (§2.1), producer requirements
(§2.2) that a V=1 consumer could still satisfy by construction,
sanitization char class (§2.3), and comment grammar (§6.1). A V≥2
producer emitting richer payloads still gets those bytes sanitized
and embedded by a V=1 consumer without a new error path. Removing a
previously-valid character from the sanitization class, narrowing the
accepted key type, or repurposing a comment-grammar field is a major
version bump and triggers the deprecation window above.

8.3 Consumer behaviour on unavailable or malformed tags

Whether the producer is a V=1, V≥2, or entirely unknown implementation:
if the env var named by claims_env= is absent, the serial is
malformed, the key is inaccessible (perms, timeout, revoked), or the
payload sanitizes to empty, the consumer skips the tag and proceeds
with the session. This is fail-open by design and consistent with
claims_env being an optional forensic-correlation channel rather
than an authentication factor.

Observability of these skip paths is intentionally tiered so SIEM
dashboards see only signals that indicate producer-side bugs:

    Malformed serial (non-decimal, out of int32 range)
        pam_syslog(LOG_WARNING, "authnft: claims env '%s' not a
        valid key serial", env)

    keyctl read failure (EACCES, EKEYEXPIRED, EKEYREVOKED, ENOKEY)
        pam_syslog(LOG_WARNING, "authnft: keyctl_read(serial=%ld)
        failed: %m", serial)

    Env var absent or empty
        No log. This is the non-misconfiguration "no producer ran"
        case and would be the single loudest source of warning spam
        on stacks where claims_env is declared optional.

    Payload sanitizes to empty
        DEBUG build only. Rare in practice; likely indicates binary
        garbage from a non-compliant producer. Promote to WARNING
        if you observe it in the field.

The error asymmetry in CONTRIBUTING.txt invariant #4 (open_session
strict, close_session best-effort) applies to invariant-level
failures — seccomp, cgroup resolution, fragment validation. It does
not extend to optional metadata channels; claims_env unavailability
never denies a session.


9. Reporting contract ambiguities
---------------------------------
